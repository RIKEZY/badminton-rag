## 二、结论

共 4 个 P0、12 个 P1，其余为 P2。最该先修的不是 UI，而是三件事：

1. **检索链路会静默给出错结果**：切块跨章节合并、BM25 零分块被当成命中、向量缓存只校验块数。
2. **部署回滚不可靠**：回滚只重启主服务，备份路径还可能选错，健康检查容易误判。
3. **外部 API 边界缺少防护**：空 `choices`、空 `usage`、异常被宽泛吞掉，生产上会变成崩溃或静默降级。

## 三、P0：优先修

### P0-1 切块会把引言块和后续章节粘在一起

- 位置：`chunker.py:152-159`
- 问题：`same_parent = prev_parent == curr_parent or not prev_parent`，引言块 `clause=""` 时 `not prev_parent` 永远为真；同时 `len("".split(".")) == 1`，后续 `14.2.x` 的 3 段编号永远不满足“更短”条件，`prev["clause"]` 一直是空。
- 后果：一个引言块会连续吞掉后面所有条款，直到达到 `max_len`；章节前缀和页码仍停留在第一块，引用页码会错。
- 修法：引言块首次吸收条款时强制写入该条款编号；`same_parent` 增加 `prev["chapter"] == c["chapter"]` 约束。

### P0-2 向量缓存只比对块数，语料改了也会复用旧向量

- 位置：`index_builder.py:106-108`
- 问题：`if len(vecs) == len(chunks)` 就认为缓存有效。
- 后果：只改文字、不改块数时，旧向量继续对应新文本，检索结果静默错误；换 embedding 模型但维度相同也发现不了。
- 修法：缓存有效性至少同时校验 `CHUNK_CACHE` mtime、语料文件集合和 embedding 模型名/维度；更稳妥的是用内容哈希做缓存键。

### P0-3 BM25 零分块被塞进 RRF 融合

- 位置：`hybrid.py:60-62`
- 问题：`bm25.get_scores()` 对没有命中任何词的块返回 `0.0`，代码仍按分数排序取前 `k` 个，零分块按原始下标顺序进入结果。
- 后果：术语直查没有命中时，会把语料最前面的几个块当成“命中”送入 RRF，正好污染最需要精确匹配的场景。
- 修法：只保留 `score > 0` 的结果；没有正分就返回空列表，让这一路不投票。

### P0-4 回滚没有真正恢复系统

- 位置：`scripts/deploy.sh:249-252`、`scripts/deploy.sh:356-357`
- 问题：
  - 回滚只 `systemctl restart ${SERVICE_NAME}`，没有重启 `${ADMIN_SERVICE_NAME}`，后台仍跑坏版本。
  - `tar -xzf` 覆盖式解包，不会删除失败版本新增的文件。
  - `BACKUP_PATH` 用 `ls -1t | head -n 1` 重新猜，而不是使用刚才备份脚本生成的确切文件名；并发部署或目录变动时可能回滚到错误备份。
- 修法：回滚同时重启两个服务；备份脚本返回确切路径并直接复用；长期方案是解包到临时目录后整体切换。

## 四、P1：应该修

### P1-1 生成层对 API 返回没有防护

- 位置：`answer_generator.py:101`、`answer_generator.py:137`
- 问题：`resp.choices[0]`、`resp.usage.total_tokens` 直接解引用；`generate_stream` 用 `except Exception` 兜底 `stream_options`，把鉴权、限流、网络错误也吞掉，并重新发一次付费请求。
- 后果：供应商返回空 `choices` 或 `usage=None` 时直接崩；真实故障被伪装成“兼容层不支持”，还会双倍计费。
- 修法：对 `choices`、`content`、`usage` 做空值保护；只捕获 `BadRequestError` 等“参数不支持”错误并记录日志。

### P1-2 切块参数非法会死循环

- 位置：`document_loader.py:108-111`
- 问题：`chunk_text` 不校验 `size` / `overlap`，`overlap >= size` 时 `step <= 0`，`while` 永远前进不了。
- 后果：构建索引时内存持续增长，最终 OOM。
- 修法：函数入口校验 `size > 0` 且 `0 <= overlap < size`；空文本返回 `[]`。

### P1-3 装备型号模糊查询会返回任意球拍

- 位置：`tools/equipment_query.py:40`、`agent_tools.py:33`
- 问题：`normalize()` 不去掉 `%`，`LIKE '%%%'` 会匹配全表；`agent_tools.query_racket()` 又直接取 `rows[0]` 并标记 `found=True`。
- 后果：用户输入不完整型号或 `%` 时，系统会把最短型号名的球拍当成确定答案。
- 修法：转义 LIKE 元字符并声明 `ESCAPE`；多行命中时返回候选列表或要求上层追问。

### P1-4 管理后台密码可无限尝试

- 位置：`admin/admin_app.py:38`
- 问题：`pwd == PASSWORD` 明文比较，没有失败计数、退避或锁定。
- 后果：后台一旦公网可达，可被暴力破解。
- 修法：`secrets.compare_digest`；在反向代理或应用层加限流/退避。

### P1-5 查询日志的统计口径有时区错误

- 位置：`tools/query_log.py:51`、`tools/query_log.py:73`、`tools/query_log.py:131`
- 问题：写入用 `datetime.now()`（本地时间），查询用 SQLite `date('now')`（UTC）。
- 后果：在东八区，凌晨 0-8 点的提问会被算到前一天，“今日”指标长期偏差。
- 修法：统一存 UTC 并统一按 UTC 比较，或写入和查询都用 `localtime`。

### P1-6 会话 ID 只有 32 位随机量

- 位置：`tools/query_log.py:93`
- 问题：`uuid.uuid4().hex[:8]` 只有 8 个十六进制字符。
- 后果：约 7.7 万个会话后碰撞概率接近 50%，不同用户的追问链会被合并。
- 修法：存完整 UUID，展示时再截短。

### P1-7 评测脚本会重复记录结果

- 位置：`run_eval.py:181`、`run_eval.py:202`
- 问题：检索判定后先 `details.append()`，生成回答抛异常时 `except` 又追加一次。
- 后果：同一道题可能同时以命中和未命中出现，最终“未命中列表”重复。
- 修法：每道题只在一个路径记录结果；生成失败单独标记，不回滚检索判定。

### P1-8 评测脚本会破坏数字开头的改写

- 位置：`run_eval.py:103`
- 问题：`lstrip("0123456789.-、) ")` 把参数当字符集合，`60-second interval` 会变成 `second interval`。
- 后果：带数字的检索语句被改坏，评测结果失真。
- 修法：用正则只去掉真正的编号前缀，例如 `^\d+\s*[.、)-]\s*`。

### P1-9 部署通道关闭了 SSH 主机校验

- 位置：`scripts/deploy.sh:84-85`
- 问题：`StrictHostKeyChecking=no` + `UserKnownHostsFile=/dev/null`。
- 后果：上传 `.env`、执行远程 `sudo` 的通道没有 MITM 防护。
- 修法：`StrictHostKeyChecking=accept-new` + 固定 `known_hosts` 文件。

### P1-10 部署健康检查容易误判

- 位置：`scripts/deploy.sh:190`、`scripts/deploy.sh:228`
- 问题：固定 `sleep 8` 后只 curl 一次；日志用 `grep -Eqi 'error|traceback'`，`errors=0`、`error_handler` 都会命中。
- 后果：冷启动慢时误回滚；正常日志也可能触发回滚。
- 修法：有限次重试轮询；日志匹配锚定日志级别和 `Traceback (most recent call last)`。

### P1-11 `app.py` 的检索统计仍然不可信

- 位置：`app.py:397`、`app.py:263`、`app.py:41`
- 问题：
  - v1 路径 `hit=True` 硬编码，空结果也记命中。
  - 重排 `best.get(i, 0.0)` 把负分压成 0，负分块并列后顺序随机。
  - `RERANK_POOL=int(...)` 在 import 阶段解析，非法环境变量会让应用起不来。
- 后果：命中率永远 100%；换重排模型后排序静默劣化；配置写错直接白屏。
- 修法：`bool(hits)`；负无穷初始化；导入时容错解析并保证 pool >= top_k。

### P1-12 `agent_core.py` 的异常和配置边界仍会静默降级

- 位置：`agent_core.py:172`、`agent_core.py:40-52`、`agent_core.py:201`
- 问题：
  - 决策调用和 JSON 解析共用一个 `except Exception`，API 故障被伪装成正常决策。
  - `_env_num` 接受 `nan` / `inf`，`LOW_RELEVANCE=nan` 会让低相关度警告永远不触发。
  - 工具调用和结果格式化共用一个 `try`，格式化 bug 会被报告成“工具执行失败”。
- 后果：线上故障不可见，拒答策略可能失效。
- 修法：区分配置异常、传输异常和解析异常；`math.isfinite` 校验浮点；缩小 `try` 范围并记录日志。

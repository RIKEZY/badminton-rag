# 面试话术

> 用法：每个技术点练到能**不看稿讲 2 分钟**。
> 结构统一：**问题 → 做法 → 数据 → 代价**。有代价才可信。

---

# 开场：30 秒介绍项目

> 我做了一个羽毛球知识问答系统。用户用中文提问，系统从 BWF 官方规则、裁判手册、技术教学等 10 份文档里检索，生成带页码的回答。
>
> 现在语料 649 块、35.8 万字，80 道评测题里可答命中 98.6%、拒答 100%，线上跑在 AWS 上。
>
> 我重点做了三件事：跨语言检索、文档类型冲突的重排、以及 Agent 决策循环。

**不要说**「我用 RAG 做了个问答系统」——太泛，面试官听过一百遍。

---

# 技术点 1：结构感知切块

**一句话**：按文档的条款编号切，不按字数切。

**展开**：

> 最初按固定字数切，会切断句子——比如 `he side having...`，前半句在上一块。BWF 规则有天然编号（`9.1.6.`），改成按条款边界切，边界就干净了。没有编号的文档自动回退到段落切块。
>
> 另外每块要拼上层级前缀 `[Law 9 SERVICE > 9.1]`。因为 `9.1.6` 单独看只有一句「球必须低于 1.15 米」——低于什么的？前缀来自文档原文，不是模型生成的。

**数据**：649 块，平均 550 字/块

**代价**：只对有编号的文档有效

**追问预案**：
- Q：如果文档格式乱怎么办？→ 回退到段落切块，按 800 字上限切
- Q：为什么不按语义切块？→ 语义切块要调模型，成本高且不稳定；条款编号是文档自带的确定性边界

# 技术点 2：页眉清洗

**一句话**：PDF 每页的页眉污染了 BM25，清洗后召回从 6/10 到 9/10。

**展开**：

> BWF 的 PDF 每页都有页眉 `BWF Statutes, Section 4.1: Law of Badminton Page X of 14`。这些词——BWF、Law、Badminton——在 BM25 里是高频词，会被误判为强相关，挤占 top5 名额。
>
> 清洗掉整行之后，召回从 6/10 提到 9/10。

**数据**：6/10 → 9/10

**代价**：清洗规则依赖文档格式，换一种 PDF 可能要重写

**追问预案**：
- Q：为什么不用 IDF 自动降权？→ 理论上可以，但页眉是确定性噪声，直接删比调参更可靠

---

# 技术点 3：双语双路 + 两级 RRF

**一句话**：中文问题查中文块、英文改写查英文块；两侧先各自融合再平权合并。

**展开**：

> 语料一半是英文 BWF 官方规则，一半是中文技术资料。中文原问直接查英文块效果差，所以做了跨语言改写：一次调用生成 3 个英文表述。
>
> 这样就有 8 路检索：中文 2 路（向量 + BM25），英文 6 路（3 表述 × 2）。
>
> 后来又加了一路**术语直查**——中文术语查表转成英文术语，不经过模型，共 9 路。
>
> **但平铺会出问题**：英文 6 路、中文 2 路、术语 1 路，英文块天然多拿 3 倍投票权——不是因为更相关，是因为路数多。所以改成两级融合：先组内融合，再跨组平权合并。

**数据**：9 路检索，三组各取 top10 再融合

**代价**：检索次数从 2 路变 9 路；术语路单独成路会被改写路稀释，必须独立成组

**追问预案**：
- Q：为什么用 RRF 不用加权求和？→ 不同检索的分数没有可比性（向量是余弦相似度，BM25 是无界分数），RRF 只看排名，天然规避量纲问题
- Q：candidate_k 怎么定的？→ 10。太小会在跨语言融合时候选池不够，太大引入噪声

---

# 技术点 4：多表述改写

**一句话**：`temperature=0` 也不确定，所以用 3 个表述做冗余覆盖。

**展开**：

> 这里有个反直觉的发现：同一问题连跑 5 次，3 次改写出 `toss`、2 次没出，导致 Recall 在 7-9 之间摆动。
>
> `temperature=0` 理论上应该完全确定，但实测不是。我推测是推理框架的批处理带来浮点非确定性——没法证明，但现象稳定复现。
>
> 解法是：一次调用输出 3 个不同表述，用冗余覆盖不确定性。波动从 ±2 降到 ±1。

**数据**：波动 ±2 → ±1

**代价**：路数增加

**追问预案**：
- Q：为什么不重试到稳定？→ 重试也是随机的，成本更高；多表述是并行的一次性覆盖
- Q：怎么知道哪个表述好？→ 不知道，所以让 RRF 投票

# 技术点 5：语料扩容 + 重排（最推荐讲这个）

**一句话**：语料从 82 块扩到 649 块后，出现「同一概念多份文档」的问题，用重排解决，89% → 94%。

**展开**：

> 原来只有 82 块语料，top5 能覆盖 6%，系统几乎不会失败——**检索策略的差异测不出来**。所以我扩到 649 块，加了 6 份 BWF 官方文档（裁判手册、赛事规程、裁判用语等）。
>
> 扩完出现了新问题：**同一个概念有好几份文档**。比如「60 秒间歇」，规则条文讲「什么时候有」，裁判手册讲「裁判要做什么」。语义都很近，向量检索分不开，结果裁判手册挤掉了规则条文，正确答案从第 2 名掉到第 6 名。
>
> 我试过两个方案。**调权重不行**——权重适合「同一规则的官方版 vs 本土化解读」，那种情况谁更权威是明确的；但规则条文和裁判手册是**不同视角**，没有谁更权威，压了裁判手册的权重，问「裁判该怎么做」时就答不出来了。
>
> 所以用重排：融合后取 20 条候选，用交叉编码器精排。交叉编码器能判断「这段文字是否回答了这个问题」，双塔只能判断「语义是否相近」。
>
> 实测同一问题，规则条文 rerank 得 0.7259，裁判手册 0.0001——**向量检索给这两块的分数是同一量级，一刀切开**。

**数据**：89% → 94%，各跑 3 次零波动，成本 +0.22s/题（+9%）

**代价**：每题多一次 API 调用

**追问预案**：
- Q：为什么不用更大的 top_k？→ top5 是给模型看的，多了会稀释注意力，且 token 成本上升
- Q：重排模型选型？→ bge-reranker-v2-m3，免费、中文效果好
- Q：20 条候选怎么定的？→ 经验值。太少重排没空间，太多延迟上升

# 技术点 6：查询路由

**一句话**：装备参数是精确查询，不能走向量检索。

**展开**：

> 用户问「ASTROX 88S PRO 4U 多少磅」，如果走向量检索会出问题。34 款球拍里 `88S PRO`、`88D TOUR`、`88S TOUR` 的参数几乎完全相同，向量距离极近，top5 必然混着返回，模型很可能引用错型号。
>
> 实测对比很干净：
> - 问 100ZZ 磅数：SQL ✅、向量 ✅
> - 问 88S PRO 磅数：SQL ✅、向量 ❌「资料中没有提到」
>
> 所以装备走 SQLite 精确查询，文档走向量检索，中间加一层路由判断。
>
> 还有个坑：官网存的是 `ASTROX 100 ZZ`（带空格），用户输 `100ZZ`。不做归一化，精确查询会大面积失败。

**数据**：34 款球拍，10 个参数

**代价**：多一套数据结构；归一化需要维护

**追问预案**：
- Q：路由判断错了怎么办？→ 解析失败自动降级到文档检索，行为退化为 v1，不会更差
- Q：为什么不让模型生成参数？→ 型号、磅数这类精确值，生成一遍就有改写风险。模板直出 + 明细附后可核对

# 技术点 7：Agent 决策循环（最能体现判断力）

**一句话**：一次性路由不是 Agent，因为它看不到中间结果。

**展开**：

> 我最初实现的是「路由」：模型在开头判断一次该调哪个工具，然后无条件执行完。
>
> 后来发现两个问题。第一，执行中看不到结果，查询未命中就结束了——比如问「雷霆99 的磅数」，装备库没收录，它就直接说没有，不会想到改用文档检索查同系列。第二，多个工具的结果是**分别生成再拼接**的，同一份回答会自相矛盾：第一段说「88S PRO 适合进攻」，第二段说「资料中没有提到这款球拍」。
>
> 所以改成决策循环：每轮模型看到已有观察，决定下一步查什么，或者判断「够了」直接答。所有证据合并成一份，只生成一次。
>
> 判断标准很硬：**模型参与决策几次？能看到上一步结果吗？能改主意吗？** 三个都是「是」才叫 Agent。

**数据**：最多 3 轮，带重复调用检测

**代价**：多轮 LLM 调用，延迟增加

**追问预案**：
- Q：怎么防止死循环？→ 轮次上限 + 重复调用检测（相同 action + 参数直接终止）
- Q：为什么不直接用 function calling API？→ 可以用，本质相同。手写循环是为了把「观察结果怎么组织给模型」控制在自己手里
- Q：3 轮够吗？→ 目前的问题最多 2 轮。3 轮是上限，实际由模型自己判断何时停

# 技术点 8：工程化（被问「怎么保证质量」时讲）

**一句话**：68 项自动化测试、部署带回滚、日志与代码分离。

**展开**：

> 上线过程中遇到过一次崩溃：本地用 `python agent_core.py` 测没问题，推上服务器就报 Streamlit 元素 ID 重复。
>
> 根因是 Streamlit 把 app.py 当脚本执行，`import app` 会把整个脚本再跑一遍，侧边栏控件重复注册。更隐蔽的是——项目有 `pages/` 目录时，Streamlit 走另一条分支，`__main__` 不注册进 `sys.modules`，所以检测失效。
>
> 修完之后我把 Streamlit 官方的 AppTest 加进了测试套件，这个错误以后在推送前就会被拦住。
>
> 另外做了三件事：部署脚本带备份和健康检查，失败自动回滚；日志放 `/var/lib` 而不是代码目录，避免回滚覆盖用户数据；每天自动备份，用 SQLite 的 backup API 保证事务一致。

**数据**：68 项离线测试，4 项 API 测试

**代价**：测试要维护；CI 不能跑 API 测试（成本和不稳定性）

# 技术点 9：拒答——测的不是检索，是「会不会编」

**一句话**：语料没有答案时，系统要承认不知道。我拿 9 道超纲题测它，修之前只对 7 道。

**展开**：

最危险的不是「不知道」，是「用不相关的内容硬凑答案」。失败的那道长这样：

> 问：双打老是撞拍怎么办（战术问题）
> 答：双打撞拍多因站位与轮转不清。规则上，发球时双方须站对角发球区…
>     …发球顺序为右区球员发偶数分…缺证据：撞拍的具体方法未给出

**先编结论、再堆 5 条无关规则、末尾补免责。** 用户读到第一句就以为答了，
而且它引的条款号全是真的——**有出处的错误答案，比没有答案更糟**。

还发现一个更隐蔽的：「安赛龙的身高」这类题，模型**一次工具都没调**就答「没有找到相关信息」。
用户分不清「查了没有」和「压根没查」。

**数据**：拒答正确率 7/9 → 9/9，可答命中率没有退化（70/71）。

**代价**：两处 prompt 变长，每次多几十 token；首轮强制检索让「明显查不到」的问题多花约 3 秒。

**追问预案**：

> Q：为什么不在检索层直接卡分数，低于阈值就拒答？
>
> A：试过。可答题 top1 在 0.91 以上，拒答题大多在 0.18 以下，中间是真空的，0.3 能切干净。
> 但「男单世界第一」这道得了 0.61——它命中了「世界排名系统的定义」，语义相关却不回答问题。
> 这类只能靠模型判断，分数抓不住。所以分数阈值只用来加警示，最终判断还是交给模型。

> Q：怎么保证模型下次不再犯？
>
> A：保证不了。所以加了代码强制：零观察时 `answer` 动作无效，直接改成 `search_docs`。
> prompt 是软约束，代码是硬约束——这和术语拼接是同一个道理。

# 必讲的一段：我否决过自己的方案

**这段最值钱，主动讲。**

> 中间我做过一个方案：把复合问题拆成多个子查询分别检索。单题验证是有效的——问「球拍和羽毛球分别有哪些规格限制」，原来答一半，改完答全了。
>
> 但扩到 8 道对照题，**收益归零**。
>
> 原因是语料只有 82 块，top5 能覆盖 6%，系统本来就不容易失败，检索策略没有优化空间。
>
> 所以我判断：**当前瓶颈在语料规模，不在检索策略**，先扩数据再谈优化。后来扩到 649 块，问题才真正暴露出来。

**为什么讲这个**：它证明你会用数据否定自己，而不是加了功能就宣称有效。

# 高频追问

**Q：这个项目最难的地方是什么？**

> 不是某个算法，是**判断「哪里出了问题」**。同一个「答不出来」，可能是语料没有、检索没找到、路由判断错、生成答歪——四种修法完全不同。日志里现在只有 `hit=0` 一个布尔值，分不出来。这是我下一步要改的。

**Q：如果重做一次？**

> 先量化失败率再设计解法。这次是先想做 Agentic RAG，再去找失败案例，结果 4 道「该失败」的题全过了——在没病灶的地方动手术。

**Q：为什么不用 LangChain？**

> 核心工作是检索策略调优，框架会隐藏细节。手写 4000 行能说清每一步为什么这么做；用框架出问题只能猜。

**Q：怎么评估效果？**

> 18 道题，Recall@5。分老题（规则/技术/装备）和新题（裁判/赛事/跨文档）两组，每组跑 3 次看稳定性。判定条件踩过坑——写窄了会制造假失败，比如只认英文来源，但中文块里也有答案。

**Q：有真实用户吗？**

> 上线了但还没有真实流量。我做了查询日志，记录问题、路由、耗时、是否命中，准备用真实提问来验证。现在的评测集是自己出的，覆盖面和真实分布肯定有偏差。

**Q：这个项目能扩展到多大？**

> 现在 649 块用内存里的向量矩阵就够了。到 10 万块要换向量数据库（如 Milvus / Qdrant），因为暴力计算余弦相似度会变慢。BM25 也要换成 ES 或 OpenSearch。

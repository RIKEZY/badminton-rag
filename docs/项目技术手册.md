# 第一部分：这个项目到底在干什么

## 一句话

**用户用中文问羽毛球相关的问题，系统从一堆英文官方文档和中文资料里找到相关段落，然后基于这些段落生成回答，并标注出处。**

## 为什么需要它（不用它会怎样）

假设你直接把 35 万字资料丢给大模型，问「反手高远球击球点在哪」，会发生什么？

1. **塞不进去**：35 万字约 50 万 token，超出模型上下文窗口
2. **塞进去也没用**：即使能塞，模型在 50 万字里找一句话，准确率极低（这叫「大海捞针」问题）
3. **会编**：模型找不到时会「编一个听起来合理的答案」，这叫**幻觉**

所以需要一套机制：**先找，再答**。这就是 RAG。

## 系统的两个视角

| 视角 | 看到什么 |
|:---|:---|
| **用户** | 输入框 → 等几秒 → 一段带页码的回答 |
| **系统** | 问题 → 改写 → 多路检索 → 融合 → 重排 → 拼上下文 → 生成 → 答案 |

# 第二部分：术语表（按难度分组）

## A 组：AI 基础

| 术语 | 英文 | 通俗解释 |
|:---|:---|:---|
| **大语言模型** | LLM | 像 DeepSeek、GPT 这种，能理解和生成文字的模型。它只会做一件事：**根据前面的文字，预测下一个字** |
| **Token** | — | 模型处理文字的最小单位。中文约 1 字 = 1~1.5 token。**计费和限速都按 token 算** |
| **Prompt** | 提示词 | 你给模型的指令。分 `system`（角色设定）和 `user`（具体问题）两种 |
| **幻觉** | Hallucination | 模型不知道答案时，编一个看起来很合理的答案。**RAG 主要就是为了压制这个** |
| **上下文窗口** | Context window | 模型一次能读多少 token。超出就塞不进去 |

## B 组：检索技术（这个项目的核心）

| 术语 | 英文 | 通俗解释 |
|:---|:---|:---|
| **切块** | Chunking | 把长文档切成小块（本项平均 550 字/块）。为什么切？因为检索的单位是「块」，不是「整篇文档」 |
| **向量** | Vector / Embedding | 把一段文字变成一串数字（本项是 1024 个数字）。**意思相近的文字，数字也相近** |
| **向量检索** | Vector search | 把问题也变成向量，然后找「数字最接近」的块。**能理解同义词**，比如「击球点」和「hitting point」 |
| **余弦相似度** | Cosine similarity | 衡量两个向量有多接近的算法。值越大越像 |
| **BM25** | — | 传统关键词检索算法。**看词出现了没有、出现几次**。不懂同义词，但精确匹配很强 |
| **分词** | Tokenize | 把句子切成词。中文用 jieba（「反手高远球」→「反手」「高远」「球」） |
| **召回** | Recall | 「该找到的，找到了几个」。Recall@5 = 正确答案在返回的 5 条里的比例 |
| **RRF** | Reciprocal Rank Fusion | 把多路检索结果合并的算法。**只看排名，不看分数**（因为不同检索的分数没法比） |
| **重排** | Rerank | 粗筛之后再精排。用一个更慢但更准的模型，重新给候选打分 |
| **交叉编码器** | Cross-encoder | 重排用的模型类型。**把问题和文档一起输入**，直接判断「这段文字回答了这个问题吗」 |
| **双塔模型** | Bi-encoder | 向量检索用的模型类型。**问题和文档分别编码**，只能算「像不像」，判断不了「答没答」 |

### 双塔 vs 交叉编码：这是本项目最重要的一个区分

```
双塔（向量检索）：
   问题 → [编码器] → 向量 A
   文档 → [编码器] → 向量 B
   比较 A 和 B 的距离
   ✅ 快（文档可以预先编码好）
   ❌ 只能判断「语义相近」，判断不了「是否回答了问题」

交叉编码（重排）：
   [问题 + 文档] → [编码器] → 一个分数
   ✅ 准（能看到问题和文档的交互）
   ❌ 慢（每个候选都要重新算一遍，不能预先建索引）
```

**所以流程是：双塔粗筛 20 条 → 交叉编码精排 5 条。**

## C 组：Agent

| 术语 | 英文 | 通俗解释 |
|:---|:---|:---|
| **Agent** | 智能体 | 能自己决定「下一步做什么」的程序。**关键特征：能看到上一步的结果，据此改变计划** |
| **工具调用** | Tool calling | 模型输出一个结构化指令（「调用 query_racket，参数是 88S PRO」），程序执行后把结果返回给模型 |
| **决策循环** | Agent loop | 决策 → 执行 → 观察 → 再决策，直到够了为止 |
| **固定流水线** | Pipeline | 步骤写死，模型只在某一步参与。**这不是 Agent** |

### 判断是不是 Agent 的三个问题

1. 模型参与决策几次？**1 次 = 流水线，多次 = Agent**
2. 模型能看到上一步的结果吗？**看不到 = 流水线**
3. 模型能改变主意吗？**不能 = 流水线**

## D 组：工程

| 术语 | 通俗解释 |
|:---|:---|
| **索引** | 预先算好的数据结构，让检索变快。本项有两个：向量矩阵（.npy）和 BM25 索引 |
| **缓存** | 算过一次就存下来，下次直接读。本项的切块结果和向量都缓存成文件 |
| **Streamlit** | Python 的网页框架。**写 Python 就能出网页，不用写前端** |
| **systemd** | Linux 的服务管理器。负责「开机自启、挂了自动重启」 |
| **nginx** | 反向代理。把公网 80 端口的请求转发到本机 8501 端口 |
| **CI/CD** | 持续集成 / 持续部署。**CI** = 推代码自动跑测试；**CD** = 自动部署 |
| **pytest** | Python 的测试框架。写 `test_xxx()` 函数，运行 `pytest` 自动执行 |
| **SQLite** | 单文件数据库。不需要装服务，一个 `.db` 文件就是一个库 |

# 第三部分：一个问题走完全程

以「反手高远球的击球点应该在身体哪个位置？」为例。

## 步骤 1：改写（1 次 LLM 调用）

**输入**：中文问题
**输出**：3 个英文表述

```
1. Where should the hitting point be for a backhand clear?
2. What is the correct contact point for a backhand clear in badminton?
3. Where is the ideal strike point when playing a backhand overhead clear?
```

**为什么要改写**：语料里 40 块是英文 BWF 规则。中文问题直接查英文块，效果差。

## 步骤 2：八路检索

| 路径 | 用什么查 | 查什么 |
|:---|:---|:---|
| 中文侧 1 | 向量检索 | 中文原问 |
| 中文侧 2 | BM25 | 中文原问 |
| 英文侧 1-2 | 向量 + BM25 | 英文表述 1 |
| 英文侧 3-4 | 向量 + BM25 | 英文表述 2 |
| 英文侧 5-6 | 向量 + BM25 | 英文表述 3 |

**共 8 路，每路取 20 个候选。**

## 步骤 3：语言内融合（RRF）

中文 2 路 → 融合成 1 个排名
英文 6 路 → 融合成 1 个排名

**为什么先分语言**：8 路平铺的话，英文 6 路 vs 中文 2 路，英文块天然多拿 3 倍投票权——不是因为更相关，是因为路数多。

## 步骤 4：跨语言融合（RRF）

中文 top10 + 英文 top10 → 融合 → 取 20 条候选

## 步骤 5：重排（1 次 API 调用）

20 条候选 → 交叉编码器逐条打分 → 取 top5

**实测效果**：问「60 秒间歇」，规则条文得 0.7259，裁判手册得 0.0001——**向量检索给这两块的分数是同一量级，分不开**。

## 步骤 6：拼上下文

5 个块拼成一段文字，每块带来源标记：

```
[规则] badminton_rules.pdf 第10页
[Law 16.2.1] ... 60 seconds interval ...

[裁判] bwf_itto.txt 第1页
[Law 5.4.10] ... during the interval ...
```

## 步骤 7：生成（1 次 LLM 调用）

**输入**：上下文 + 原问题
**输出**：带页码的回答

# 第四部分：八个技术决策

每个决策都是「遇到问题 → 试方案 → 用数据验证」。

## 决策 1：结构感知切块

**问题**：按固定字数切，会切断句子（`he side having...`）

**做法**：BWF 规则有天然编号（`9.1.6.`），按条款边界切

**代价**：只对有编号的文档有效，无编号的回退到段落切块

## 决策 2：页眉清洗

**问题**：PDF 每页有 `BWF Statutes, Section 4.1: Law of Badminton Page X of 14`，含 BWF/Law/Badminton 等高频词，BM25 会误判为强相关

**数据**：清洗前 6/10，清洗后 9/10

**代价**：清洗规则依赖文档格式，换一种 PDF 可能要重写

## 决策 3：双语双路

**问题**：中文语料被英文查询漏掉

**做法**：中文原问查中文块，英文改写查英文块

**代价**：检索次数从 2 路变 8 路，耗时增加

## 决策 4：两级 RRF

**问题**：8 路平铺，英文侧 6 路天然占优

**做法**：先语言内融合，再跨语言融合，两侧平权

**代价**：多一层计算，且 `candidate_k` 要调（太小会丢召回）

## 决策 5：多表述改写

**问题**：`temperature=0` 也不确定——同一问题连跑 5 次，3 次含 `toss`、2 次不含，Recall 在 7-9 之间摆动

**做法**：一次调用输出 3 个表述，用冗余覆盖不确定性

**数据**：波动从 ±2 降到 ±1

**代价**：检索路数从 2 变 8

## 决策 6：重排（而不是调权重）

**问题**：扩语料后出现「同一概念多份文档」——规则条文（是什么）、裁判手册（怎么做）、赛事规程（怎么管）。语义都近，但只有一份是答案

**两个方案的区分**：

| 方案 | 适用 | 为什么 |
|:---|:---|:---|
| 权重 | 同一规则的官方版 vs 本土化解读 | 谁更权威是明确的 |
| **重排** | 规则 / 手册 / 规程 | **没有谁更权威，只有「哪个回答了问题」** |

**数据**：89% → 94%

**代价**：+0.22s/题（+9%）

## 决策 7：装备走 SQL 不走向量

**问题**：34 款球拍里 `88S PRO` / `88D TOUR` / `88S TOUR` 参数几乎相同，向量距离极近

**实测**：

| 问题 | SQL | 向量 |
|:---|:---|:---|
| 100ZZ 4U 磅数 | ✅ | ✅ |
| 88S PRO 4U 磅数 | ✅ | ❌「资料中没有」 |

**代价**：多一套数据结构 + 型号归一化（官网存 `ASTROX 100 ZZ`，用户输 `100ZZ`）

## 决策 8：Agent 要循环，不要路由

**问题**：一次性路由，执行中看不到结果，查询未命中就结束

**实测对比**：

| 问题 | 一次性路由 | 决策循环 |
|:---|:---|:---|
| 雷霆99 的磅数 | 未收录 → 直接说没有 | 未收录 → **改用文档检索查同系列** |
| 88S PRO 适合进攻 + 拍面尺寸 | 装备、文档各自生成 → **自相矛盾** | 合并生成 → 一段话讲完 |

**代价**：多轮 LLM 调用，延迟增加；需要轮次上限和重复调用检测

# 第五部分：评测怎么做

## 指标：Recall@5

**定义**：正确答案在返回的 5 条里的比例。

**为什么不用准确率**：RAG 有两个环节（检索、生成），要分开测。检索没找到，生成再强也没用。

## 评测集的坑（踩过三次）

**判定条件写窄会制造假失败**：

| 题 | 原判定 | 问题 |
|:---|:---|:---|
| 单打发球区 | 只认 `badminton_rules.pdf` | 答案在 wiki 中文块也有 |
| 头顶 vs 反手 | 关键词「主动性」 | 实际写的是「主动攻击性」 |
| 羽毛球规格 | 只认 `badminton_rules.pdf p2` | 答案在 wiki 也有 |

**修法**：期望来源写成列表，任一命中即算通过。

## 对照实验

**单次运行不可靠**——改写有非确定性。所以每个配置跑 3 次，看是否稳定。

| 配置 | 老题 | 新题 | 合计 |
|:---|:---|:---|:---|
| 无重排 | 9/10 | 7/8 | 16/18 = 89% |
| 有重排 | 10/10 | 7/8 | 17/18 = 94% |

**三次跑结果完全一致**，说明不是运气。

```
pytest              → 离线测试（不调 API）
pytest -m api       → 调 API 的测试

```

# 第七部分：这个项目不会什么（诚实边界）

| 不会 | 原因 |
|:---|:---|
| 回答语料里没有的内容 | 会明确说「资料中没有」，这是设计目标不是缺陷 |
| 图片里的信息 | PDF 里的图片文字提取不到（如场地长度 13.40 米） |
| 多跳推理 | 「A 决定 B」这类需要链式推理的问题，现在只能靠多轮检索勉强覆盖 |
| 精确计算 | 不擅长数值比较（如「两款拍磅数差多少」目前只罗列不算差值） |
| 实时数据 | 没有接实时赛程、排名接口 |
| 大规模 | 649 块是当前上限，扩到 10 万块需要换向量数据库 |

# 附：常被追问的问题

**Q：为什么不用 LangChain / LlamaIndex？**
A：本项核心是「检索策略调优」，框架会隐藏细节。手写 4000 行能说清每一步为什么这么做；用框架出问题只能猜。

**Q：为什么用 SQLite 不用 PostgreSQL？**
A：34 款球拍 + 日活个位数。SQLite 零运维、单文件、支持事务，完全够用。上 PG 是给运维添麻烦。

**Q：为什么不微调模型？**
A：微调解决的是「风格和格式」，解决不了「知识更新」和「引用出处」。而且本项的数据量（35 万字）远不够微调。

**Q：最大的技术难点是什么？**
A：不是某个算法，是**判断「哪里出了问题」**。同一个「答不出来」，可能是语料没有、检索没找到、路由判断错、生成答歪——四种修法完全不同。日志里只有 `hit=0` 一个布尔值，分不出来。

**Q：如果重做一次，会改什么？**
A：先量化失败率再设计解法。这次是先想做 Agentic RAG，再去找失败案例，结果 4 道「该失败」的题全过了——**在没病灶的地方动手术**。

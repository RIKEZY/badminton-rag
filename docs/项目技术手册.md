# 第一部分：这个项目到底在干什么

## 一句话

**用户用中文问羽毛球相关的问题，系统从一堆英文官方文档和中文资料里找到相关段落，然后基于这些段落生成回答，并标注出处。**

## 为什么需要它（不用它会怎样）

假设你直接把 35 万字资料丢给大模型，问「反手高远球击球点在哪」，会发生什么？

1. **塞不进去**：35 万字约 50 万 token，超出模型上下文窗口
2. **塞进去也没用**：即使能塞，模型在 50 万字里找一句话，准确率极低（这叫「大海捞针」问题）
3. **会编**：模型找不到时会「编一个听起来合理的答案」，这叫**幻觉**

所以需要一套机制：**先找，再答**。这就是 RAG。

## 系统的两个视角

| 视角 | 看到什么 |
|:---|:---|
| **用户** | 输入框 → 等几秒 → 一段带页码的回答 |
| **系统** | 问题 → 改写 → 多路检索 → 融合 → 重排 → 拼上下文 → 生成 → 答案 |

# 第二部分：术语表（按难度分组）

## A 组：AI 基础

| 术语 | 英文 | 通俗解释 |
|:---|:---|:---|
| **大语言模型** | LLM | 像 DeepSeek、GPT 这种，能理解和生成文字的模型。它只会做一件事：**根据前面的文字，预测下一个字** |
| **Token** | — | 模型处理文字的最小单位。中文约 1 字 = 1~1.5 token。**计费和限速都按 token 算** |
| **Prompt** | 提示词 | 你给模型的指令。分 `system`（角色设定）和 `user`（具体问题）两种 |
| **幻觉** | Hallucination | 模型不知道答案时，编一个看起来很合理的答案。**RAG 主要就是为了压制这个** |
| **上下文窗口** | Context window | 模型一次能读多少 token。超出就塞不进去 |

## B 组：检索技术（这个项目的核心）

| 术语 | 英文 | 通俗解释 |
|:---|:---|:---|
| **切块** | Chunking | 把长文档切成小块（本项平均 550 字/块）。为什么切？因为检索的单位是「块」，不是「整篇文档」 |
| **向量** | Vector / Embedding | 把一段文字变成一串数字（本项是 1024 个数字）。**意思相近的文字，数字也相近** |
| **向量检索** | Vector search | 把问题也变成向量，然后找「数字最接近」的块。**能理解同义词**，比如「击球点」和「hitting point」 |
| **余弦相似度** | Cosine similarity | 衡量两个向量有多接近的算法。值越大越像 |
| **BM25** | — | 传统关键词检索算法。**看词出现了没有、出现几次**。不懂同义词，但精确匹配很强 |
| **分词** | Tokenize | 把句子切成词。中文用 jieba（「反手高远球」→「反手」「高远」「球」） |
| **召回** | Recall | 「该找到的，找到了几个」。Recall@5 = 正确答案在返回的 5 条里的比例 |
| **RRF** | Reciprocal Rank Fusion | 把多路检索结果合并的算法。**只看排名，不看分数**（因为不同检索的分数没法比） |
| **重排** | Rerank | 粗筛之后再精排。用一个更慢但更准的模型，重新给候选打分 |
| **交叉编码器** | Cross-encoder | 重排用的模型类型。**把问题和文档一起输入**，直接判断「这段文字回答了这个问题吗」 |
| **双塔模型** | Bi-encoder | 向量检索用的模型类型。**问题和文档分别编码**，只能算「像不像」，判断不了「答没答」 |

### 双塔 vs 交叉编码：这是本项目最重要的一个区分

```
双塔（向量检索）：
   问题 → [编码器] → 向量 A
   文档 → [编码器] → 向量 B
   比较 A 和 B 的距离
   ✅ 快（文档可以预先编码好）
   ❌ 只能判断「语义相近」，判断不了「是否回答了问题」

交叉编码（重排）：
   [问题 + 文档] → [编码器] → 一个分数
   ✅ 准（能看到问题和文档的交互）
   ❌ 慢（每个候选都要重新算一遍，不能预先建索引）
```

**所以流程是：双塔粗筛 20 条 → 交叉编码精排 5 条。**

## C 组：Agent

| 术语 | 英文 | 通俗解释 |
|:---|:---|:---|
| **Agent** | 智能体 | 能自己决定「下一步做什么」的程序。**关键特征：能看到上一步的结果，据此改变计划** |
| **工具调用** | Tool calling | 模型输出一个结构化指令（「调用 query_racket，参数是 88S PRO」），程序执行后把结果返回给模型 |
| **决策循环** | Agent loop | 决策 → 执行 → 观察 → 再决策，直到够了为止 |
| **固定流水线** | Pipeline | 步骤写死，模型只在某一步参与。**这不是 Agent** |

### 判断是不是 Agent 的三个问题

1. 模型参与决策几次？**1 次 = 流水线，多次 = Agent**
2. 模型能看到上一步的结果吗？**看不到 = 流水线**
3. 模型能改变主意吗？**不能 = 流水线**

## D 组：工程

| 术语 | 通俗解释 |
|:---|:---|
| **索引** | 预先算好的数据结构，让检索变快。本项有两个：向量矩阵（.npy）和 BM25 索引 |
| **缓存** | 算过一次就存下来，下次直接读。本项的切块结果和向量都缓存成文件 |
| **Streamlit** | Python 的网页框架。**写 Python 就能出网页，不用写前端** |
| **systemd** | Linux 的服务管理器。负责「开机自启、挂了自动重启」 |
| **nginx** | 反向代理。把公网 80 端口的请求转发到本机 8501 端口 |
| **CI/CD** | 持续集成 / 持续部署。**CI** = 推代码自动跑测试；**CD** = 自动部署 |
| **pytest** | Python 的测试框架。写 `test_xxx()` 函数，运行 `pytest` 自动执行 |
| **SQLite** | 单文件数据库。不需要装服务，一个 `.db` 文件就是一个库 |

# 第三部分：一个问题走完全程

以「反手高远球的击球点应该在身体哪个位置？」为例。

## 步骤 1：术语识别 + 改写（1 次 LLM 调用）

**先查表**（不调 LLM，0 毫秒）：中文术语 → 英文术语

```
反手高远球的击球点应该在身体哪个位置？
  → clear（高远球）、SHUTTLE
```

查的是 `tools/term_map.json`，78 条映射，由 48 个 BWF 章节标题反推生成。

**为什么要查表**：中文表达发散——「换边」可以说换场、交换场地，但 BWF 文档里只有 `change ends`。
自由翻译会得到 `switch sides`，BM25 一个都匹配不上。

**再交给模型改写**，术语作为 user message 的一部分：

```
用户问题：反手高远球的击球点应该在身体哪个位置？
【本次必须使用的术语】clear / SHUTTLE
改写时围绕这些术语组织句子，不要用同义替换。
```

**输出**：3 个英文表述，每条末尾再拼一次术语（兜底，防止模型没照做）

```
1. Where should the hitting point be for a backhand clear? clear
2. What is the correct contact point for a backhand clear in badminton? clear
3. Where is the ideal strike point when playing a backhand overhead clear? clear
```

**为什么要改写**：语料里大部分块是英文 BWF 文档，中文问题直接查英文块效果差。

## 步骤 2：九路检索（并行）

| 路径 | 用什么查 | 查什么 |
|:---|:---|:---|
| 中文侧 1-2 | 向量 + BM25 | 中文原问 |
| 英文侧 1-6 | 向量 + BM25 | 3 条英文改写各 2 路 |
| **术语侧** | BM25 | 映射表给的英文术语 |

**共 9 路，每路取 20 个候选。**

**并行执行**：4 次 embedding 调用并发，串行 1.6 秒 → 并行 0.4 秒；
其余 5 路是 BM25 本地计算，毫秒级。

## 步骤 3：组内融合（RRF）

中文 2 路 → 1 个排名
英文 6 路 → 1 个排名
术语 1 路 → 1 个排名

**为什么先分组**：9 路平铺的话，英文 6 路 vs 中文 2 路，英文块天然多拿 3 倍投票权——
不是因为更相关，是因为路数多。

**为什么术语单独成组**：试过并进英文侧，结果被 6 路改写稀释——术语路本身排第 1，融合后进不了 top5。

## 步骤 4：跨组融合（RRF）

中文 top10 + 英文 top10 + 术语 top10 → 融合 → 取 20 条候选

## 步骤 5：重排（2 次 API 调用）

20 条候选 → 交叉编码器逐条打分 → 取 top5

**为什么要打两次分**：rerank 模型有同语言偏好。实测「球落在边线上算出界吗」：

| 块 | 中文 query | 英文 query |
|:---|:---|:---|
| wiki「出界情形」（中文） | **0.42** | 0.015 |
| 规则「界外判定」（英文） | 0.006 | **0.63** |

语料 500+ 块是英文，只用中文 query 会系统性压掉英文块。
所以中文原问和第一条英文改写各打一次，逐块取最高分。

**另一类靠重排解决的问题**：问「60 秒间歇」，规则条文得 0.7259，裁判手册得 0.0001——
**向量检索给这两块的分数是同一量级，分不开**。


## 步骤 6：拼上下文

5 个块拼成一段文字，每块带来源标记：

```
[规则] badminton_rules.pdf 第10页
[Law 16.2.1] ... 60 seconds interval ...

[裁判] bwf_itto.txt 第1页
[Law 5.4.10] ... during the interval ...
```

## 步骤 7：生成（1 次 LLM 调用）

**输入**：上下文 + 原问题
**输出**：带页码的回答

# 第四部分：十个技术决策

每个决策都是「遇到问题 → 试方案 → 用数据验证」。

## 决策 1：结构感知切块

**问题**：按固定字数切，会切断句子（`he side having...`）

**做法**：BWF 规则有天然编号（`9.1.6.`），按条款边界切

**代价**：只对有编号的文档有效，无编号的回退到段落切块

## 决策 2：页眉清洗

**问题**：PDF 每页有 `BWF Statutes, Section 4.1: Law of Badminton Page X of 14`，含 BWF/Law/Badminton 等高频词，BM25 会误判为强相关

**数据**：清洗前 6/10，清洗后 9/10

**代价**：清洗规则依赖文档格式，换一种 PDF 可能要重写

## 决策 3：双语双路

**问题**：中文语料被英文查询漏掉

**做法**：中文原问查中文块，英文改写查英文块

**代价**：检索次数从 2 路变 9 路（含后来加的术语直查），耗时增加

## 决策 4：两级 RRF

**问题**：9 路平铺，英文侧 6 路天然占优

**做法**：先语言内融合，再跨语言融合，两侧平权

**代价**：多一层计算，且 `candidate_k` 要调（太小会丢召回）

## 决策 5：多表述改写

**问题**：`temperature=0` 也不确定——同一问题连跑 5 次，3 次含 `toss`、2 次不含，Recall 在 7-9 之间摆动

**做法**：一次调用输出 3 个表述，用冗余覆盖不确定性

**数据**：波动从 ±2 降到 ±1

**代价**：检索路数从 2 变 8

## 决策 6：重排（而不是调权重）

**问题**：扩语料后出现「同一概念多份文档」——规则条文（是什么）、裁判手册（怎么做）、赛事规程（怎么管）。语义都近，但只有一份是答案

**两个方案的区分**：

| 方案 | 适用 | 为什么 |
|:---|:---|:---|
| 权重 | 同一规则的官方版 vs 本土化解读 | 谁更权威是明确的 |
| **重排** | 规则 / 手册 / 规程 | **没有谁更权威，只有「哪个回答了问题」** |

**数据**：89% → 94%

**代价**：+0.22s/题（+9%）

## 决策 7：装备走 SQL 不走向量

**问题**：34 款球拍里 `88S PRO` / `88D TOUR` / `88S TOUR` 参数几乎相同，向量距离极近

**实测**：

| 问题 | SQL | 向量 |
|:---|:---|:---|
| 100ZZ 4U 磅数 | ✅ | ✅ |
| 88S PRO 4U 磅数 | ✅ | ❌「资料中没有」 |

**代价**：多一套数据结构 + 型号归一化（官网存 `ASTROX 100 ZZ`，用户输 `100ZZ`）

## 决策 8：Agent 要循环，不要路由

**问题**：一次性路由，执行中看不到结果，查询未命中就结束

**实测对比**：

| 问题 | 一次性路由 | 决策循环 |
|:---|:---|:---|
| 雷霆99 的磅数 | 未收录 → 直接说没有 | 未收录 → **改用文档检索查同系列** |
| 88S PRO 适合进攻 + 拍面尺寸 | 装备、文档各自生成 → **自相矛盾** | 合并生成 → 一段话讲完 |

**代价**：多轮 LLM 调用，延迟增加；需要轮次上限和重复调用检测

## 决策 9：术语要靠映射，不能靠翻译

**问题**：中文表达发散，同一个意思有多种说法；但 BWF 文档用的是固定术语。
「换边」可以写成换场、交换场地，文档里只有 `change ends`。

**实测**：同一问题跑 3 次，改写分别是 `end change` / `end-change` / `side-switching`，
检索命中 1/2/2 次——**措辞一变结果就翻**。

**试过三种做法**：

| 做法 | 效果 | 结论 |
|:---|:---|:---|
| prompt 里列术语，要求复用 | 改写统一成 `change ends`，换边稳定了 | 软约束，模型可能不照做 |
| 术语单独一路检索 | 「边线」能命中，但只有 1 票 | 打不过 6 路改写，融合后被稀释 |
| **检测到术语就强制拼进每条改写** | 「边线」的 3 条改写从 1/3 命中变 3/3 | **采用** |

**关键**：RRF 是按路数投票的。同样一个术语信号，单独成路只有 1 票，拼进 3 条改写有 6 票。

**最终三者并存**：prompt 约束（让改写自然带上）+ 术语独立路（改写失效时兜底）+ 强制拼接（保证出现）。

**代价**：改写结果变长，检索池里多一路噪声；需要维护 78 条映射表。

## 决策 10：拒答要靠硬约束，不能只靠 prompt

**问题**：语料没有答案时，模型会用「相关内容」硬凑答案。

**实测**：问「双打老是撞拍怎么办」（战术问题），它答「撞拍多因站位不清」，
再堆 5 条发球站位规则，末尾补一句免责。**先编结论、再堆证据、免责垫底**——
用户读到第一句就以为答了，而且引的条款号全是真的。

**还有一个更隐蔽的**：「安赛龙的身高」这类题，模型一次工具都没调就答「没有找到相关信息」。
用户分不清「查了没有」和「压根没查」。

**做法**：

| 缺陷 | 修法 |
|:---|:---|
| 用相关内容硬答 | prompt 加「直接回答 vs 只是相关」的判断步骤 + 正反例；检索最高分 < 0.3 时在证据前加警示 |
| 没查就说没有 | prompt 写明首轮必须调工具 + **代码强制**（零观察时 `answer` 无效） |

**为什么代码还要再兜一层**：prompt 是软约束。这和决策 9 的「强制拼接」是同一个道理。

**数据**：拒答 7/9 → 9/9，可答命中率不变

**代价**：prompt 变长；首轮强制检索让「明显查不到」的问题多花约 3 秒

# 第五部分：评测怎么做

## 指标：Recall@5

**定义**：正确答案在返回的 5 条里的比例。

**为什么不用准确率**：RAG 有两个环节（检索、生成），要分开测。检索没找到，生成再强也没用。

## 评测集的坑（踩过三次）

**判定条件写窄会制造假失败**：

| 题 | 原判定 | 问题 |
|:---|:---|:---|
| 单打发球区 | 只认 `badminton_rules.pdf` | 答案在 wiki 中文块也有 |
| 头顶 vs 反手 | 关键词「主动性」 | 实际写的是「主动攻击性」 |
| 羽毛球规格 | 只认 `badminton_rules.pdf p2` | 答案在 wiki 也有 |

**修法**：期望来源写成列表，任一命中即算通过。

## 对照实验

**单次运行不可靠**——改写有非确定性。所以每个配置跑 3 次，看是否稳定。

| 配置 | 老题 | 新题 | 合计 |
|:---|:---|:---|:---|
| 无重排 | 9/10 | 7/8 | 16/18 = 89% |
| 有重排 | 10/10 | 7/8 | 17/18 = 94% |

**三次跑结果完全一致**，说明不是运气。

## 当前结果：80 题四组

18 题太小，而且题目都是自己出的、偏「能答对的」。扩到 80 题，按考察维度分四组，
每组 17-18 道可答 + 2-3 道拒答：

| 组 | 可答命中 | 拒答正确 |
|:---|:---|:---|
| A 单点事实 | 17/18 | 2/2 |
| B 口语化 | 18/18 | 2/2 |
| C 跨文档 | 17/17 | 3/3 |
| D 深度细节 | 18/18 | 2/2 |
| **合计** | **70/71 = 98.6%** | **9/9 = 100%** |

## 拒答题：测的不是检索，是「会不会编」

语料里没有答案时，正确行为是承认不知道。修之前是 7/9，失败的那道长这样：

```
问：双打老是撞拍怎么办（战术问题）
答：双打撞拍多因站位与轮转不清。规则上，发球时双方须站对角发球区…
    …发球顺序为右区球员发偶数分…缺证据：撞拍的具体方法未给出
```

**先编结论、再堆 5 条无关规则、末尾补免责。** 用户读到第一句就以为答了——
这类「有出处但答非所问」比直接说不知道危险得多。

还发现另一个问题：「安赛龙的身高」这类题，模型**一次工具都没调**就答「没有找到相关信息」。
用户无法区分「查了没有」和「压根没查」。

两个缺陷，两种修法：

| 缺陷 | 根因 | 修法 |
|:---|:---|:---|
| 用相关内容硬答 | prompt 只说「没有就说不知道」，没区分「直接回答」和「只是相关」 | prompt 加判断步骤 + 正反例；检索最高分 < 0.3 时在证据前加警示 |
| 没查就说没有 | 模型凭「这类信息资料里大概没有」的猜测就结束 | prompt 写明首轮必须调工具 + **代码强制** |

**为什么代码还要再强制一层**：prompt 是软约束，模型可能不遵守。这和「术语拼接」是同一个道理。

阈值 0.3 是量出来的：

```
可答题 top1：0.91 ~ 0.99
拒答题 top1：0.007 ~ 0.18（仅「男单世界第一」0.61，它命中了「排名系统定义」）
```

中间几乎是真空的。但 0.61 那道抓不到——「语义相关却不回答」只能靠 prompt 判断。


**为什么分两类**：CI 里不能调 API（花钱、不稳定），但切块、SQL、归一化这些纯逻辑必须自动测。

## CI（GitHub Actions）

```
.github/workflows/ci.yml
```

推送 / PR / 手动触发时自动执行四步：

1. 语法检查（compileall）
2. **无缓存重建索引**，断言 649 块
3. pytest 离线测试
4. 敏感文件检查（`.env` / `.db` / `.npy` / `html_cache`）

**机制**：不是有人手动跑，是 GitHub 读到这个文件后自己起一台临时机器执行。
之前每次手动跑 pytest，是因为仓库里没这个文件。

**为什么不跑 API 测试**：要真实 key、有费用、结果不稳定。CI 只跑确定性的部分。

**为什么加「无缓存重建索引」**：`chunks_v2.json` 不在仓库里（每次生成都会变），
CI 环境是干净的。这一步既验证切块逻辑，又回答「换台机器能不能重建索引」。

# 第七部分：这个项目不会什么（诚实边界）

| 不会 | 原因 |
|:---|:---|
| 回答语料里没有的内容 | 会明确说「资料中没有」，这是设计目标不是缺陷 |
| 图片里的信息 | PDF 里的图片文字提取不到（如场地长度 13.40 米） |
| 多跳推理 | 「A 决定 B」这类需要链式推理的问题，现在只能靠多轮检索勉强覆盖 |
| 精确计算 | 不擅长数值比较（如「两款拍磅数差多少」目前只罗列不算差值） |
| 实时数据 | 没有接实时赛程、排名接口 |
| 大规模 | 649 块是当前上限，扩到 10 万块需要换向量数据库 |

# 附：常被追问的问题

**Q：为什么不用 LangChain / LlamaIndex？**
A：本项核心是「检索策略调优」，框架会隐藏细节。手写 4000 行能说清每一步为什么这么做；用框架出问题只能猜。

**Q：为什么用 SQLite 不用 PostgreSQL？**
A：34 款球拍 + 日活个位数。SQLite 零运维、单文件、支持事务，完全够用。上 PG 是给运维添麻烦。

**Q：为什么不微调模型？**
A：微调解决的是「风格和格式」，解决不了「知识更新」和「引用出处」。而且本项的数据量（35 万字）远不够微调。

**Q：最大的技术难点是什么？**
A：不是某个算法，是**判断「哪里出了问题」**。同一个「答不出来」，可能是语料没有、检索没找到、路由判断错、生成答歪——四种修法完全不同。日志里只有 `hit=0` 一个布尔值，分不出来。

**Q：如果重做一次，会改什么？**
A：先量化失败率再设计解法。这次是先想做 Agentic RAG，再去找失败案例，结果 4 道「该失败」的题全过了——**在没病灶的地方动手术**。

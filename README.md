# 🏸 羽毛球知识助手

基于 RAG 的中文问答系统，覆盖**规则条文、技术动作、装备参数、裁判执行、赛事规程**五类语料，回答时标注出处页码。

不是"上传 PDF 然后聊天"的玩具 demo——这个项目处理了跨语言检索、文档结构切块、LLM 输出不确定性、多文档同概念排序四个真实问题，并且每一步改动都有数据验证。

## 效果

| 指标 | 数值 |
|:---|:---|
| **Recall@5** | **17/18（94%）**（三次重复验证，零波动） |
| 语料 | 649 块 / 约 31 万字 / 10 个来源 |
| 重排 | bge-reranker-v2-m3，+0.22s/题，召回 +5.6% |
| 单次问答延迟 | 6-12 秒（含 2 次 LLM 调用） |

> 评测集 18 题：规则 4、技术 3、装备 2、裁判 4、赛事 2、术语 1、跨文档 1、数值 1。
> **扩语料前是 82 块 / 10 题 10/10；扩到 649 块后掉到 9/10，加重排后回到 10/10（老题），新题 7/8。**

## 技术架构

```
用户提问（中文）
    ↓
查询改写 · 1 次 LLM 调用 → 3 个不同英文表述
    ↓
┌──────────────────┬────────────────────┐
│   中文侧 · 2 路   │   英文侧 · 6 路     │
│ 向量(bge-m3)     │ 3 表述 × (向量+BM25) │
│ BM25(jieba 分词) │                    │
└──────────────────┴────────────────────┘
    ↓ 语言内 RRF（各取 top10）
    ↓ 跨语言 RRF（中英平权）→ 候选 20 条
    ↓ cross-encoder 重排（bge-reranker-v2-m3）
最终 top5 → 拼上下文（带条款前缀）→ 生成回答
```

**为什么分成中英两侧**：语料是英文 BWF 官方规则 + 中文技术/装备资料。单一语言的查询只能覆盖一半语料，中文原问查中文块、英文改写查英文块，两路都要。

**为什么是两级融合**：8 路平铺融合时，英文侧 6 路、中文侧 2 路，英文块天然多拿 3 倍投票权——不是因为更相关，是因为路数多。两级融合让每种语言作为一个整体参与竞争。

**为什么融合后还要重排**：扩语料后出现「同一概念多份文档」——规则条文（是什么）、裁判手册（怎么做）、赛事规程（怎么管）。三者语义都近，向量分不开。实测问「60 秒间歇」，规则条文 rerank 得分 0.7259，裁判手册 0.0001，交叉编码器能判断「这段文字是否回答了这个问题」，双塔只能判断「语义是否相近」。

## Agent 路由

装备参数是**精确查询**，不能走向量检索——34 款球拍里 `ASTROX 88S PRO` / `88D TOUR` / `88S TOUR` 的参数几乎相同，向量距离极近，top5 必然混着返回。

```
用户提问
   ↓
路由（LLM 输出结构化 JSON）
   ├─ 具体型号  → query_racket  → SQLite 精确查询 → 模板直出参数
   └─ 泛化问题  → search_docs   → 向量检索 + 重排 → 模型生成
```

| 设计 | 为什么 |
|:---|:---|
| 装备参数**不过 LLM** | 型号、磅数这类精确值，生成一遍就有改写风险。模板直出 + 明细附后可核对 |
| 但**要过 LLM 推理** | 用户问「88S PRO 适合打进攻吗」，只给参数是答非所问。参数作为证据进 prompt，模型做判断并说明依据 |
| 型号**归一化匹配** | 官网存 `ASTROX 100 ZZ`，用户输 `100ZZ`。不做归一化，精确查询在实际使用中会大面积失败 |
| 路由**失败降级** | 解析失败自动退回 `search_docs`，行为退化为 v1，不会更差 |

## 关键设计决策

| 决策 | 为什么 |
|:---|:---|
| **结构感知切块** | BWF 规则有天然编号（`9.1.6.`），按条款切边界干净；按字符切会切在句子中间（`he side having...`）。无编号文档自动回退到段落切块。 |
| **页眉清洗** | PDF 每页有 `BWF Statutes, Section 4.1: Law of Badminton Page X of 14`，含 BWF/Law/Badminton 等高频词，会被 BM25 误判为强相关，挤占 top5 名额。 |
| **层级前缀** | 每块拼上 `[Law 9 SERVICE > 9.1]`。`9.1.6` 单独看只有一句「球必须低于 1.15 米」——低于什么的？前缀来自文档原文，不是模型生成。 |
| **多路改写** | 实测 `temperature=0` 也不保证确定性：同一问题连跑 5 次，3 次含 `toss`、2 次不含，导致 Recall 在 7-9 之间摆动。推测原因是推理框架的批处理带来浮点非确定性。改成一次调用输出 3 个表述，用冗余覆盖不确定性。 |
| **不做分库路由** | 文档之间不做分库——语义检索本身就能把类型分对（技术题全中技术块，装备题全中装备块），分库反而引入风险：分类错误会导致「完全答不出」。**但按查询类型分流是必要的**（精确型号 vs 泛化问题），那是数据形态不同，不是文档主题不同。 |
| **重排而非权重** | 权重适合「同一规则的官方版 vs 本土化解读」——谁更权威是明确的。但规则条文 / 裁判手册 / 赛事规程是**不同视角**，没有谁更权威，只有「哪个回答了这个问题」。压权重会让「裁判该怎么做」这类问题答不出来。 |
| **装备走 SQL 不走向量** | 精确查询用语义检索会返回「相似型号」而非「那一个型号」。实测问 `88S PRO 磅数`，向量检索答「资料中没有提到」，SQL 精确命中 `[20,28]`。 |

### 三个反直觉的结论

**① 收益最大的改动不涉及算法**

| 优化项 | 投入 | 收益 |
|:---|:---|:---|
| 查询改写 | 10 行 | +1 题 |
| BM25 + RRF | 40 行 | 0 题 |
| **页眉清洗** | **3 行** | **+3 题** |
| **删冗余语料** | **0 行** | **+2 题** |

**② 混合检索会挤掉正确结果**

加 BM25 融合后，某题从命中变成失败——融合把原本正确的块挤出了 top5。RRF 不是只增不减。

**③ 判定标准比指标本身重要**

早期只看「文件名 + 页码」判定命中，9/10 里有 4 个假命中（页眉块、同页不同块）。改成「文件名 + 页码±1 + 关键词」三重校验后，真实基线是 6/10。**虚高的数字比没有数字更危险。**

## 已知限制

1. **图片信息提取不到**：场地长度 `13.40 米` 只存在于 Diagram A 的图片里，pypdf 提取纯文本抓不到。需 OCR 或多模态解析。
2. **列表型规则易漏兜底条款**：Law 14.2 有 7 项，模型答出 6 项，稳定漏掉最后一条「任何不可预见情况」。这是可预测的失败模式，不是偶发。
3. **评测集难度中等**：未包含多跳推理（需两块拼合）和跨文档综合题。
4. **跨页块的页码精度下降**：合并后记起始页，Law 6 跨第 4-5 页，引用时会说"第4页"。

## 快速开始

```bash
# 1. 安装依赖
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# 2. 配置密钥
copy .env.example .env
# 编辑 .env，填入 SILICONFLOW_API_KEY / DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL / DEEPSEEK_MODEL

# 3. 启动 Web 界面
.venv\Scripts\python -m streamlit run app.py

# 4. 跑评测
.venv\Scripts\python run_eval.py
```

## 技术栈

| 环节 | 选型 | 说明 |
|:---|:---|:---|
| Embedding | `BAAI/bge-m3`（硅基流动） | 多语言，模型本身免费 |
| 生成 | `DeepSeek-V4.1-Flash`（硅基流动） | 关闭思考阶段，首字延迟 0.37s |
| 检索 | 向量 + BM25 + RRF | BM25 用 jieba 做中文分词 |
| 界面 | Streamlit | 纯 Python，无需前端 |

> ⚠️ `openai` SDK 必须用 1.x。3.x 改了 `content` 的序列化方式（把字符串包成列表），部分 OpenAI 兼容层会因此返回 400。
